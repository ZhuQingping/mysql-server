# WL#012: PQ Dependent-Ref Join & Dynamic Partition

## Summary

Enable dependent-ref (ref key depends on outer table) tables to be selected
as the divided table in parallel join. Workers dynamically partition the
ref table during execution based on the actual ref key values from the
outer table, rather than requiring pre-determined scan boundaries.

## Motivation

Previously, only tables with pre-determined scan ranges could be selected
as the divided table. This excluded large tables accessed via dependent-ref
(e.g., `t1 JOIN t2 ON t1.a = t2.b` where t2 uses an index on b). In TPC-H
Q5, the customer table is large but uses a dependent-ref index, forcing PQ
to select the tiny region table instead, yielding no parallelism benefit.

## Specification

### Problem Statement

```
SELECT * FROM t1 JOIN t2 ON t1.a = t2.b WHERE t1.b = 1
```

- t2 uses index `idx_b(b)` with key depending on `t1.a`
- t2 cannot be pre-partitioned because its scan range is unknown before
  execution
- Only t1 can be selected as divided table, even if t1 is small

### Solution: Dynamic Partition by Workers

1. In the optimization stage, dependent-ref tables can be selected as
   the divided table
2. The leader does NOT partition the ref table
3. Workers partition the ref table during execution, when the actual ref
   key values are known
4. After partition, data blocks are executed in parallel by multiple workers
5. A ref key query range is partitioned only once
6. One worker can execute multiple different ref key data blocks

### Divided Table Selection Rule

**Previous rule:** Select the single table with the largest fetch rows.

**New rule:** Consider dependent-ref tables and use cumulative row count:

```
For join order t1 x t2 x t3 x t4:
- If t1.fetch_rows >= threshold: select t1
- If t1.fetch_rows * t2.fetch_rows * t3.fetch_rows >= threshold: select t3
- etc.
```

This allows selecting a large dependent-ref table that appears later in
the join order.

### Data Block Manager

**Global management (leader side):**

A single `PQ_Range` queue managed by the leader. For non-ref tables, ranges
are generated by the leader before execution. For ref tables, ranges are
generated by workers during execution and submitted to the leader's queue.

**Local management (worker side):**

Each worker maintains a `PQ_Ctx` dual queue (current + standby). For the
first execution with a given ref key, the worker obtains `PQ_Range` from
the leader and generates `PQ_Ctx`. For subsequent executions (same ref
key in nested-loop join), the worker reuses its local `PQ_Ctx` queue.

This ensures that each worker scans the same data across multiple join
rounds.

### PQRefIterator

A new iterator `PQRefIterator` encapsulates the dynamic partition and
read logic:

```c++
PQRefIterator::Read() {
  if (m_first_record_since_init) {    // new ref key value
    construct_lookup_ref(thd, table, m_ref)      // 1. construct ref key
    if (pq_ref_key_map.count(key) == 0) {         // 2. check global hash
      pq_ref_key_map[key] = true;                 // 2.1 record this ref key
      table()->file->pq_ref_build_ranges(...)     // 2.2 partition the ref table
    }
    table()->file->ha_pq_next(...)                // 3. read from partition block
  } else {
    table()->file->ha_pq_next(...)                // 4. continue reading
  }
}
```

### Global Hash for Deduplication

A global hash map (`pq_ref_key_map`) prevents the same ref key from being
partitioned multiple times by different workers. When a worker encounters
a new ref key, it checks the hash. If absent, the worker partitions and
records the key. If present, the worker directly reads the existing blocks.

### ref_key Optimization in PQ_Ctx

Each `PQ_Ctx` stores a `pq_ref_key` object. During nested-loop join, the
worker first compares `PQ_Ctx::pq_ref_key` with the current ref key. If
they differ, the PQ_Ctx is skipped entirely, avoiding expensive per-record
comparisons.

### Performance

TPC-H Q5 with dependent-ref partition: enables selecting the large customer
table as the divided table instead of the tiny region table, providing
significant parallelism improvement.
